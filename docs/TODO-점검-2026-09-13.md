# ⚠️ 철회 — 1차에서 틀리게 적었던 것

이 프로젝트의 규칙대로, 틀린 것은 지우지 않고 왜 틀렸는지를 남긴다.

## 철회 1. "실거래 추정가의 단위가 안 맞는다" — **틀렸다**

1차에서 `comparableArea`가 아파트에 `item.landArea`(대지권 면적)를 쓰는데
실거래 단가는 건물면적 기준이라 단위가 어긋난다고 적었다.

**실측으로 확인하니 아니었다.** 크롤러의 `property.area`를 400건 뜯어봤다.

```
361건  land_sqm=None  building_sqm=16.15  total_sqm=16.15   ← 집합건물: total = 전용면적
 38건  land_sqm=120.8 building_sqm=None   total_sqm=120.8   ← 토지: total = 토지면적
```

`mapCourtAuctionRow`의 `land_sqm || total_sqm` 규칙 때문에 **집합건물은 전용면적이,
토지는 토지면적이** `landArea`에 들어간다. 즉 물건 종류에 맞는 면적이 이미 들어 있다.

서울 아파트 12건으로 검산했다. `추정가 / 공시가격` 중앙값 **1.52배** — 정상 범위다.
`landArea` 중앙값도 84.7㎡로 대지권이 아니라 전용면적이다.

**왜 틀렸나:** 필드 이름이 `landArea`라는 것만 보고 내용을 확인하지 않았다.
(다만 이름은 여전히 오해를 부른다 → E-6)

## 철회 2. "`buildingArea`가 없어서 공시가격을 못 찾는다" — **영향이 과장됐다**

`item.buildingArea`가 항상 `undefined`라는 사실 자체는 맞다(C-1). 하지만
"지금 공시가 미확인의 상당수가 여기서 나온다"고 쓴 것은 근거 없는 추측이었다.

**서로 다른 PNU 30건으로 `/api/housing-price`를 실제로 불러 세어봤다.**

```
✅ 공시가격 찾음                        28건
❌ 세대목록은 있는데 동/호 매칭 실패        1건
—  그 PNU에 공동주택가격 자체가 없음        1건
```

실패한 1건도 원인이 따로 있었다 — `서울 강남구 역삼동 798-1 더힐 비동 5층501호`.
`parseUnitFromAddress`의 한글 동 허용 목록이 `[가나다라마바사아자차카타파하]`인데
**"비동"의 "비"가 없어서** 동을 못 읽었다. `area`가 갔다면 도왔겠지만 주원인은 아니다.

**결론: C-1은 "죽은 참조"로는 유효하고, 사용자 영향은 작다.** 순위를 내렸다.

## ✅ A-1. 잘못된 URL 하나로 서버 프로세스가 죽는다 [재현함 · 2차 재확인] — `1ad763d` 에서 고침

`dev-server.mjs:48`의 핸들러가 `async`라서 unhandled rejection이 되고,
Node 24 기본값이 그걸 **프로세스 종료**로 처리한다.

**재현 (2차에서 한 번 더 확인했다):**

```
GET /%E0%A4%A            → 000 (연결 끊김)
GET /api/client-config   → 000 (서버가 죽었다)
```

같은 순간 다른 포트(4173)의 별도 프로세스는 `200`이었다 — 죽은 것은 그 프로세스 하나다.

**서버 로그:**

```
URIError: URI malformed
    at decodeURIComponent (<anonymous>)
    at serveStaticFile (dev-server.mjs:61:63)
    at Server.<anonymous> (dev-server.mjs:57:9)
Node.js v24.13.0   [exited with code 1]
```

**범위:** Vercel은 `/api/`만 타므로 배포 영향은 적다. 하지만 `server.mjs`(`npm start`)가
같은 서버를 쓴다. 자체 호스팅으로 옮기는 순간 요청 한 번에 서비스가 내려간다.

**고치는 법:** `serveStaticFile` 전체를 `try/catch`로 감싸고 실패는 400으로 돌려준다.
`handleApiRequest`의 `new URL()`도 같은 이유로 감싼다(배포는 죽지 않고 500이 되지만).

## ✅ A-2. 요청 하나로 특정 지역이 5분간 "물건 없음"이 된다 [재현함] — `79cb1aa` 에서 고침

`lib/court.mjs:337` `getAllCourtAuctionRows`의 캐시 키:

```
activeFilter : requireCoordinates : sort : courtRows : courtPages : bounds
```

그런데 `lib/court.mjs:629`의 `passthrough`는 이것들을 업스트림에 실어 보낸다:

```
q, query, status, source, region, sale_date_from, sale_date_to, active, sort
```

**`q` · `region` · `status` · `source` · `sale_date_*`가 키에 없다.**
필터가 걸린 결과가 필터 없는 키에 저장된다.

**재현 (부산, 캐시 비어 있는 상태에서 시작):**

| 순서 | 요청 | properties | scannedRows |
|---|---|---|---|
| 1 | `...&sources=court&q=ZZZNOSUCHTHING` | 0 | 0 |
| 2 | `...&sources=court` ← **평범한 요청** | **0** | **0** |
| 3 | 경계를 0.01도만 옮김(다른 격자) | 1,325 | 1,750 |

3번이 대조군이다. 지역 문제가 아니라 **캐시가 오염된 것**임을 보여준다.

반대 방향도 확인했다. 서울 경계를 먼저 평범하게 부른 뒤 `q=ZZZNOSUCHTHING`을 붙여
부르면 29건이 그대로 나온다 — 즉 **`q`가 조용히 무시된다.** 어느 쪽이 먼저냐로 결과가 갈린다.

**왜 `evict()`가 못 막나:** `q` 결과는 `total=0`이라 `complete = 0 < 500 = true`가 되어
"정상적으로 다 받았다"로 판정된다.

**배포에서 더 나쁜 이유:** `gridAlignedBounds`(`lib/court.mjs:44`)는
`COURT_AUCTION_SERVER_BOUNDS_FILTER === "1"`일 때만 경계를 키에 넣는다.
로컬 `.env`에는 `=1`이 들어 있다(확인함). **Vercel 환경변수는 확인이 필요하다** —
없으면 모든 경계가 `"nationwide"` 키 하나를 공유해 요청 한 번에 전국이 빈 지도가 된다.

**고치는 법:** `passthrough` 배열과 캐시 키를 **한 곳에서 같이 만든다.**
`lib/court.mjs:29`에 이미 같은 사고의 주석이 붙어 있다 —
"지역을 키에 넣지 않으면 다른 지역 요청이 남의 목록을 그대로 받아 물건 없음이 된다."
**같은 실수가 한 파일 안에서 반복됐다.**

## ✅ G-1. 실거래 조회가 방금 채운 공시가격을 지운다 [재현함] — `8e0e449` 에서 고침

**이번 점검에서 찾은 것 중 사용자 영향이 가장 확실하다.**

`app.js:534` `hydrateReferenceData`:

```js
const pnuCount = await hydratePnu(baseLabel, tone, targetItems);
// PNU가 새로 채워진 물건은 객체가 교체됐으므로 최신 객체로 이어서 공시가격을 조회한다.
const refreshed = pnuCount ? refreshTargets(targetItems) : targetItems;
const officialCount = await hydrateOfficialPrices(baseLabel, tone, refreshed);
const dealCount     = await hydrateSeoulDeals(baseLabel, tone, refreshed);   // ← 같은 배열
```

`hydratePnu` 다음에는 `refreshTargets`로 최신 객체를 다시 집어온다. 주석까지 붙어 있다.
**그런데 `hydrateOfficialPrices` 다음에는 그러지 않는다.** `hydrateSeoulDeals`가
받는 `refreshed`는 공시가격이 채워지기 **전**의 낡은 객체들이고,

```js
updated.push({ ...item, nearbyDeals, marketDealSource, marketDealScope, checks });
...
properties = properties.map((item) => updates.get(item.id) || item);
```

이 낡은 사본이 `properties`의 최신 객체를 **통째로 덮어쓴다.**

**재현 (브라우저에서 실제 함수를 같은 순서로 호출):**

```
시작            : 공시가 0건  / 실거래 0건
공시가격 조회 후 : 공시가 19건 / 실거래 0건     (19건 반영)
실거래 조회 후   : 공시가 6건  / 실거래 55건    (55건 반영)
                  ↑ 13건이 사라졌다
```

**드러나는 증상 두 가지**

1. **화면이 깜빡인다.** 헤더의 "공시가 확인" 숫자와 카드의 "기준시가 기준" 태그가
   채워졌다가 "공시가 미확인"으로 되돌아간다.
2. **같은 API를 두 번 부른다.** 지워진 값은 다음 하이드레이션에서 다시 조회된다.
   한 화면 로딩에서 **고유 URL 41개에 요청 54번 — 13번(24%)이 낭비**였다(측정).
   VWorld·국세청 할당량이 그만큼 새고 있다.

> **주의 — 이 결론에 두 번 만에 도달했다.** 처음 "덮어쓰기가 있나" 폴링으로 재봤을 때는
> 0건이 나와서 가설을 접었다. 그때는 마침 겹치는 물건이 없어서였다.
> **폴링으로 "안 보였다"를 "없다"로 읽지 말 것.** 결국 두 함수를 직접 순서대로
> 호출해서야 잡혔다.

**고치는 법:** `hydrateOfficialPrices` 다음에도 `refreshTargets`를 한 번 더 태운다.
근본적으로는 `properties` 갱신을 "통째 교체"가 아니라 "필드 병합"으로 바꾸는 쪽이 안전하다.

## ✅ G-2. 시·도 집계 마커가 지도를 움직일 때마다 따라 움직인다 [재현함] — `7dbc969` 에서 고침

`lib/geo.mjs:247` `provincesInBounds`:

```js
const center = PROVINCE_CENTERS.find((entry) => entry[0] === name);
...
lat: center ? clamp(center[1], viewSwLat, viewNeLat) : (viewSwLat + viewNeLat) / 2,
```

`name`은 `PROVINCE_EXTENTS`에서 온다 — **전부 정식 명칭**("부산광역시").
그런데 `PROVINCE_CENTERS`는 8개를 **줄임말**로 들고 있다("부산").

**17개 중 8개가 조회에 실패한다:** 부산광역시 · 대구광역시 · 대전광역시 · 울산광역시 ·
세종특별자치시 · 강원특별자치도 · 전북특별자치도 · 제주특별자치도

실패하면 시·도 중심 대신 **화면에 걸친 사각형의 기하학적 한가운데**를 쓰므로,
화면을 움직이면 마커도 따라 움직인다.

**재현 (화면 오른쪽 끝만 조금씩 줄이며):**

```
화면 오른쪽 끝 129.40 → 부산 마커 lng=129.1020    경남 마커 lng=128.2132
화면 오른쪽 끝 129.30 → 부산 마커 lng=129.1020    경남 마커 lng=128.2132
화면 오른쪽 끝 129.20 → 부산 마커 lng=129.0910    경남 마커 lng=128.2132
화면 오른쪽 끝 129.15 → 부산 마커 lng=129.0660    경남 마커 lng=128.2132
                              ↑ 부산은 움직인다      ↑ 경남은 고정
(부산 실제 중심 129.0756 / 경남 실제 중심 128.2132)
```

**이 코드가 막으려던 것이 바로 이것이다.** 같은 함수의 주석:

> 물건 분포의 한가운데를 찍으면 경기도 마커가 서울 바로 옆에 붙어 라벨이 겹친다.
> 사람이 아는 시·도 중심을 쓰고, 화면 밖으로 나가지 않게만 잘라 준다.

의도는 맞는데 **8개는 조용히 그 의도 밖에 있었다.** `DECISIONS.md 2026-09-11`의
"시·도 중심을 제자리에 찍으면 라벨이 겹친다"는 주의사항도 이 8개에는 적용되지 않고 있다.

**고치는 법:** `PROVINCE_EXTENTS`와 `PROVINCE_CENTERS`가 같은 이름 공간을 쓰게 하거나,
찾지 못하면 조용히 넘어가지 말고 눈에 띄게 한다.

## ✅ G-3. `fetchJsonRetry`는 HTTP 오류를 재시도하지 않는다 [재현함] — `6402498` 에서 고침

**`docs/TODO-배포-공매-0건.md`가 남긴 수수께끼의 기계적 원인이다.**

`lib/util.mjs:40` `fetchJson`은 `response.ok`를 보지 않는다. 502가 와도 본문을
`JSON.parse` 하려다 실패해 `{text: "<html>..."}`를 정상 반환한다. 예외가 아니므로
`fetchJsonRetry`의 재시도 루프가 돌지 않는다.

**측정 (`attempts: 3`으로 설정하고 실제 호출 횟수를 셈):**

| 실패 모양 | 실제 fetch 호출 |
|---|---|
| **502 + HTML 본문 (VWorld 실장애 모습)** | **1번** |
| 500 + 빈 본문 | **1번** |
| 429 Too Many Requests | **1번** |
| 네트워크 자체가 끊김 (throw) | 3번 |

`DECISIONS.md 2026-09-04`는 이렇게 적어 뒀다:

> VWorld 호출은 간헐적으로 끊긴다(실측 10회 중 3회). `fetchJsonRetry`가 3회까지
> 재시도하고, 그래도 실패하면 `withUpstreamFallback`이 503과 안내 문구를 값으로 돌려준다.
> **이 두 겹을 걷어내면 공시가 칸이 통째로 비는 500이 다시 새어나온다.**

**그런데 배포에서 실제로 관측된 실패는 `regionError: "502 Bad Gateway"`다.**
즉 그 두 겹이 **이 실패 모양에는 하나도 걸리지 않는다.**

**끝까지 따라간 결과 (502를 흉내내고 `/api/land-price` 경로를 그대로 실행):**

```
ok           : true
pricePerSqm  : null
VWorld 호출  : 3번   (연도 3개 × 재시도 0)

→ dev-server 는 payload.ok 를 보고 HTTP 200 을 돌려준다
→ withUpstreamFallback 은 '예외'를 잡는 것이라 502 에는 걸리지 않는다
→ 화면은 '조회했는데 값이 없는 물건'으로 보고 officialPriceMisses 에 담는다 (영구 포기)
```

이것이 그 문서가 적은 **"`ok:true`인데 값은 `null`"의 정체**이고,
**"같은 `land-price`가 503과 200을 오갔다"**는 관측의 설명이다 —
끊기면(throw) 재시도→fallback→503, 502면 재시도 없이 200.

**고치는 법:** `fetchJson`이 `response.ok`를 확인해 5xx·429는 던지게 한다.
그러면 기존 재시도와 `withUpstreamFallback` 두 겹이 **의도대로** 동작한다.
**이것만으로 배포 공매 0건이 해결된다는 뜻은 아니다** — VWorld가 왜 502를 주는지는
여전히 미해결이다. 다만 "한 번 삐끗하면 회복이 안 되는" 층은 걷힌다.

# 남은 것

## 사용자 판단이 필요한 것

**G-5 — 4174 포트에서 네이버 지도가 안 뜬다.** 네이버 콘솔에 `http://127.0.0.1:4174`를
등록해 두 포트를 진짜로 같게 만들 것인지, 아니면 "4174는 API 전용"이라고 못박을 것인지.
어느 쪽이든 `DECISIONS.md 2026-09-13` 의 "포트만 다르고 하는 일은 같다"를 고쳐야 한다.
(G-4 를 고쳐서 지금은 최소한 대체 지도라도 뜬다 — 빈 화면은 아니다.)

**G-6 — `comparableArea` 의 고정값(빌라 59㎡ / 오피스텔 28㎡).** 실제 중앙값은
29.8㎡ / 22.1㎡ 이고 진짜 면적이 `landArea` 에 이미 있다(빌라 76%, 오피스텔 53%가
고정값에서 30% 넘게 벗어난다). 다만 이 값이 왜 들어갔는지 기록이 없다.
의도가 있었는지 확인하고 고친다.

# 확인했고 손댈 필요 없는 것

문제 목록만 남기면 다음 세션이 멀쩡한 곳을 다시 판다.

- **XSS** — `innerHTML` 17곳 + `insertAdjacentHTML` 7곳 전부 `escapeHtml`을 거친다 (B-4의 `href` 세 곳만 예외)
- **경로 탈출** — `dev-server.mjs:66`. `/../.env`, `/.env`, `/%2e%2e/.env`, `/data/*.gz` 전부 404 (재현함)
- **온비드 SSRF 호스트 검사** — `169.254.169.254` → 400 (재현함). 리다이렉트 구멍만 남았다(B-2)
- **`fetchJsonRetry`의 `AbortSignal`** — 시도마다 새로 만든다. 흔히 틀리는 곳인데 맞다
  (다만 재시도가 도는 조건 자체가 좁다 → G-3)
- **불완전 응답 축출** — `lib/court.mjs:400` `evict()`
- **`landArea` 값 자체** — 물건 종류에 맞는 면적이 들어온다 (「철회 1」에서 400건 확인)
- **`/api/housing-price` 매칭률** — 서로 다른 PNU 30건 중 28건 성공 (측정함)
- **4173에서의 화면 전체** — 지도·마커·목록·필터·상세 정상. 우리 코드에서 나온 콘솔 오류 0건
- **문법** — `node --check` 전 파일 통과
- **주석** — "왜 이렇게 했는지"를 적고 있다. **G-1·G-2·G-3은 전부 그 주석이 단서였다.**
