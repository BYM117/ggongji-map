# A. 치명 — 지금 당장 고칠 것

## A-1. 잘못된 URL 하나로 서버 프로세스가 죽는다 [재현함]

`dev-server.mjs:61`의 `decodeURIComponent`가 `URIError`를 던지는데 아무도 잡지 않는다.
`dev-server.mjs:48`의 핸들러가 `async`라서 예외가 unhandled rejection이 되고,
Node 24 기본값이 그걸 **프로세스 종료**로 처리한다.

**재현:**

```bash
curl -s -o /dev/null -w "%{http_code}\n" "http://127.0.0.1:4174/%E0%A4%A"   # 000
curl -s -o /dev/null -w "%{http_code}\n" "http://127.0.0.1:4174/"           # 000  ← 서버가 죽었다
```

**서버 로그:**

```
URIError: URI malformed
    at decodeURIComponent (<anonymous>)
    at serveStaticFile (dev-server.mjs:61:63)
    at Server.<anonymous> (dev-server.mjs:57:9)
Node.js v24.13.0
[exited with code 1]
```

**범위:** Vercel은 `/api/`만 타므로 배포 영향은 적다. 하지만 `server.mjs`(`npm start`)가
같은 서버를 쓴다. 자체 호스팅으로 옮기는 순간 요청 한 번에 서비스가 내려간다.

**고치는 법:** `serveStaticFile` 전체를 `try/catch`로 감싸고 실패는 400으로 돌려준다.
`handleApiRequest`의 `new URL()`도 같은 이유로 감싸야 한다(배포는 죽지 않고 500이 되지만).

## A-2. 요청 하나로 특정 지역이 5분간 "물건 없음"이 된다 [재현함]

`lib/court.mjs:337` `getAllCourtAuctionRows`의 캐시 키:

```
activeFilter : requireCoordinates : sort : courtRows : courtPages : bounds
```

그런데 `lib/court.mjs:629`의 `passthrough`는 이것들을 업스트림에 실어 보낸다:

```
q, query, status, source, region, sale_date_from, sale_date_to, active, sort
```

**`q` · `region` · `status` · `source` · `sale_date_*`가 키에 없다.**
필터가 걸린 결과가 필터 없는 키에 저장된다.

**재현 (부산, 캐시 비어 있는 상태에서 시작):**

| 순서 | 요청 | properties | scannedRows |
|---|---|---|---|
| 1 | `...&sources=court&q=ZZZNOSUCHTHING` | 0 | 0 |
| 2 | `...&sources=court` ← **평범한 요청** | **0** | **0** |
| 3 | 경계를 0.01도만 옮김(다른 격자) | 1,325 | 1,750 |

3번이 대조군이다. 지역 문제가 아니라 **캐시가 오염된 것**임을 보여준다.

반대 방향도 확인했다. 서울 경계를 먼저 평범하게 부른 뒤 `q=ZZZNOSUCHTHING`을 붙여
부르면 29건이 그대로 나온다 — 즉 **`q`가 조용히 무시된다.** 어느 쪽이 먼저냐에 따라
결과가 갈린다.

**왜 `evict()`가 못 막나:** `q` 결과는 `total=0`이라 `complete = 0 < 500 = true`가 되어
"정상적으로 다 받았다"로 판정된다. 불완전 캐시를 빼는 방어선이 이 경우에는 안 걸린다.

**배포에서 더 나쁜 이유:** `gridAlignedBounds`(`lib/court.mjs:44`)는
`COURT_AUCTION_SERVER_BOUNDS_FILTER === "1"`일 때만 경계를 키에 넣는다.
Vercel에 그 환경변수가 없으면 **모든 경계가 `"nationwide"` 키 하나를 공유**하므로
요청 한 번에 전국이 빈 지도가 된다. (로컬 `.env`에는 들어 있다. Vercel은 확인 필요.)

**고치는 법:** `passthrough` 배열과 캐시 키를 **한 곳에서 같이 만든다.** 지금은 두 목록이
따로 있어서 어긋난 것이다. `lib/court.mjs:29`에 이미 같은 사고의 주석이 붙어 있다 —
"지역을 키에 넣지 않으면 다른 지역 요청이 남의 목록을 그대로 받아 물건 없음이 된다."
**같은 실수가 한 파일 안에서 반복됐다.**

# B. 보안

## B-1. 인증 없는 API 키 프록시 — 할당량이 남의 것이다 [재현함]

배포 함수는 누구나 부를 수 있다. 인증·레이트리밋·CORS·Referer 검사가 **하나도 없다**
(응답 헤더는 `Cache-Control`, `Content-Type`뿐).

| 엔드포인트 | 무엇을 태우나 | 화면이 쓰나 |
|---|---|---|
| `/api/onbid` | 온비드 키 · **원문 그대로 반환** | ✗ |
| `/api/properties` | 법원 전체 + 온비드 전체 (경계 없음, 제일 비쌈) | ✗ |
| `/api/court-auctions` | 법원 API | ✗ |
| `/api/onbid-properties` | 온비드 키 | ✗ |
| `/api/geocode` | VWorld 할당량 | ✓ |
| `/api/land-price` `/api/housing-price` `/api/parcel-boundary` | VWorld 할당량 | ✓ |
| `/api/seoul-deals` | 서울 열린데이터 할당량 | ✓ |

**`/api/onbid`는 사실상 "당신 키로 돌아가는 공개 온비드 API"다.** `lib/onbid.mjs:359`가
사용자 파라미터를 그대로 붙이고 응답 원문을 돌려준다. curl로 확인했다.

`app.js`가 실제로 부르는 엔드포인트를 대조했다. **위 표의 ✗ 네 개는 한 번도 부르지 않는다.**

**고치는 법:** 먼저 ✗ 네 개를 지운다. 가장 싸고 확실한 방어다.
✓ 쪽은 별도 판단이 필요하다(여긴 화면이 실제로 쓴다).

## B-2. SSRF 호스트 검사가 리다이렉트로 우회된다 [코드 근거]

`lib/onbid-detail.mjs:287`의 허용목록 자체는 잘 동작한다 —

**첫 주소만 검사하고, 온비드가 302로 어디를 가리키든 따라간다.**

## B-3. 업스트림이 주는 주소로 무조건 302를 쏜다 [코드 근거]

크롤러 응답이 오염되면 그대로 오픈 리다이렉트다. 호스트 허용목록 한 줄로 막힌다.

## B-4. `escapeHtml`은 `javascript:`를 막지 못한다 [코드 근거]

`app.js:3197`은 `< > & " '`만 치환한다. `javascript:alert(1)`에는 그 문자가 하나도 없다.
그런데 세 곳이 외부 데이터를 `href`에 넣는다:

- `app.js:2853` — 온비드 감정평가서 `item.url`
- `app.js:2992` — 법원 문서 `doc.sourceUrl`
- `app.js:3018` — 법원 원문 링크 `detail.auction.detailUrl`

출처가 공공 API라 가능성은 낮지만 방어가 한 겹도 없다.
`http:`/`https:`만 통과시키는 `safeUrl()`을 하나 두고 세 곳에 적용한다.

**나머지 XSS 면은 상태가 좋다.** `innerHTML` 17곳과 `insertAdjacentHTML` 7곳을 전부 확인했고,
사용자·외부 문자열은 모두 `escapeHtml`을 거친다. 정적 파일 경로 탈출도 막혀 있다
(`/../.env`, `/.env`, `/%2e%2e/.env` 전부 404 — 재현함).

# C. 조용히 틀린 것 — 코드가 없는 필드를 보고 있다

## C-1. `item.rawAddress`와 `item.buildingArea`는 항상 `undefined`다 [재현함]

`lib/normalize.mjs:49` `normalizeProperty`가 돌려주는 객체에 두 필드가 **없다.**
`lib/court.mjs:538` `mapCourtAuctionRow`가 만들어 두지만 정규화에서 떨어진다.

**실제 응답으로 확인:**

```

keys: address appraisal bidDate buildingPurpose caseNo categoryConfident categoryGroup
      categorySub checks failCount id landArea landUseZone lat lng memo minBid
      nearbyDeals officialPrice officialPriceDetail officialPriceType officialPriceYear

      type zoning
```

그런데 `app.js`가 다섯 곳에서 읽는다.

**(1) `item.rawAddress || item.address`** — `app.js:686`, `app.js:707`, `app.js:1717` 외.
조용히 `address`로 떨어진다. 지금은 `address`에도 동/호가 들어 있어 대개 동작하지만,
**대괄호(목록구분·지목)가 잘린 주소로 파싱**하게 된다. 원래 의도와 다르다.

**(2) `numberFromValue(item.buildingArea) > 0`** — `app.js:672`. **영원히 false다.**
그래서 `/api/housing-price`에 `area` 파라미터가 **한 번도 가지 않는다.**
받는 쪽 `lib/vworld.mjs:212` `closestByArea`가 면적 힌트를 못 받아서,
같은 호수가 여러 동에 있고 주소의 동 표기가 API 표기와 어긋나면
`pickApartUnit`이 `null`을 돌려준다 → **공시가격 "미확인".**

> 지금 화면에 "공시가 미확인"으로 뜨는 공동주택 중 일부가 여기서 나올 가능성이 있다.
> **확인 안 함** — 몇 건인지는 세어보지 않았다. 고치기 전에 세어볼 것.

**고치는 법:** 둘 중 하나를 고른다.
- `normalizeProperty`가 `rawAddress`·`buildingArea`를 실어 보낸다 (원래 의도로 보인다), 또는
- `app.js`에서 죽은 참조를 걷어낸다.

지금은 "있는 척하는 필드"라 가장 나쁜 상태다. 다음 세션이 `buildingArea`를 믿고 코드를 짠다.

## C-2. 실패한 지오코딩을 성공처럼 캐시한다 [코드 근거]

**`docs/TODO-배포-공매-0건.md`와 직접 닿아 있다.**

`lib/vworld.mjs:326`:

```js
const point = await fetchVworldPoint(address);
const payload = point
  ? { ok: true, found: true, ... }
  : { ok: true, found: false, address };     // ← 실패도 "찾아봤는데 없음"으로
putBoundedMap(geocodeCache, address, payload, 20000);   // ← 그대로 캐시
```

`fetchVworldPoint`는 **두 가지를 똑같이 `null`로 돌려준다:**

- "그런 주소가 진짜 없다"
- "VWorld가 502를 줬다 / 타임아웃했다" (`lib/vworld.mjs:402` 데드라인, `:440` catch)

그래서 배포에서 VWorld가 흔들리는 동안 들어온 주소는 `found:false`로 굳고,
**VWorld가 회복돼도 그 인스턴스는 다시 물어보지 않는다.**

바로 아래 `fetchVworldRegion`은 같은 함정을 알고 있다:

```js
return null; // 실패는 캐시하지 않는다. 다음 요청에서 다시 시도한다.   ← lib/vworld.mjs:380
```

**두 함수가 같은 상황을 반대로 처리한다.**

브라우저도 같다. `app.js:555` `geocodeMisses`는 `payload.ok && !found`일 때 담고
**영영 지우지 않는다.** 장애 중에 접속한 세션은 그 물건을 끝까지 포기한다.

**고치는 법:** `fetchVworldPoint`가 "못 찾음"과 "못 물어봄"을 구분해 돌려주고,
후자는 캐시하지 않는다. `fetchVworldRegion`이 이미 그렇게 돼 있으니 맞추기만 하면 된다.

> **주의:** 이건 `TODO-배포-공매-0건.md`의 원인을 밝히는 것이 아니다.
> VWorld가 배포에서 왜 막는지는 여전히 미해결이다. 이건 **"한 번 막히면 회복이 안 되는"**
> 별개의 층이고, 원인 조사와 무관하게 지금 고칠 수 있다.

## C-3. 실거래 추정가의 단위가 맞지 않는다 [코드 근거]

`app.js:1335` `comparableArea`는 아파트·주택에 `item.landArea`를 쓴다 — **대지권 면적**이다.
곱하는 `medianDeal`은 `lib/seoul.mjs:157`에서 `거래금액 / ARCH_AREA`, 즉 **건물 면적당 단가**다.

```
marketValue = (원/건물㎡) × 대지권㎡      ← 단위가 어긋난다
```

실제 응답에서도 아파트 `landArea`가 68.91 / 116.97로 전용면적이 아니다.

영향 범위: 상세의 "실거래 추정가"·"실거래 대비" 두 칸, 그리고 `enrichProperty`의 `score`

> **확인 안 함** — 실제로 얼마나 어긋나는지는 재보지 않았다.
> 고치기 전에 표본 몇 건으로 "추정가 vs 실제 거래가"를 대조해 볼 것.

# 점검하면서 확인한 "괜찮은 것"

문제 목록만 남기면 다음 세션이 멀쩡한 곳을 다시 판다. 확인했고 손댈 필요 없는 것:

- **XSS** — `innerHTML` 17곳 + `insertAdjacentHTML` 7곳 전부 `escapeHtml`을 거친다 (B-4의 `href` 세 곳만 예외)
- **경로 탈출** — `dev-server.mjs:66` 방어가 동작한다. 네 가지 우회 시도 전부 404/403 (재현함)
- **온비드 SSRF 호스트 검사** — `169.254.169.254`는 400 (재현함). 리다이렉트 구멍만 남았다(B-2)
- **`fetchJsonRetry`** — 시도마다 새 `AbortSignal`을 만든다. 흔히 틀리는 곳인데 맞게 돼 있다
- **불완전 응답 축출** — `lib/court.mjs:400` `evict()`. `total`과 대조해 잘린 목록을 캐시에서 뺀다
- **문법** — `node --check` 전 파일 통과
- **주석** — "무엇을"이 아니라 "왜, 이렇게 안 하면 무엇이 깨지는지"를 적고 있다.
  **위 문제의 절반은 그 주석 덕분에 빨리 찾았다.** 이 습관을 유지할 것
