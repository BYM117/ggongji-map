# 물건 로딩이 3~5초 느려졌다

**상태:** 원인 2 해결(2026-09-13) · 원인 1은 **오진이었다** · 남은 건 콜드 스타트 하나
**측정:** 2026-09-13

---

## 한 줄로

느려진 게 아니라 **이제야 법원 물건을 실제로 받아오기 시작했다.**
전까지 쓰던 스냅샷 모드는 빨랐던 게 아니라 **0건이라 받을 게 없었다.**

그리고 남은 느림은 **서버를 깨우는 시간**이지, 받아오는 양이 아니다.

---

## 원인 1 — "100행씩 29번 받는다" 는 오진이었다

처음 이 문서는 `.env`의 `COURT_AUCTION_NUM_OF_ROWS=100` 때문에 29번 왕복한다고 적었고,
`lib/court.mjs:67`이 그 값을 읽는다고 지목했다. **둘 다 지도 화면과 무관하다.**

line 67은 `fetchCourtAuctionProperties` 안이다 — `/api/court-auctions`와 검색이 쓰는 함수다.
지도 화면이 타는 경로는 다음과 같고, 페이지 크기가 **이미 500**이다.

```
/api/viewport-properties
  → fetchCourtAuctionViewportProperties   (lib/court.mjs)
  → getAllCourtAuctionRows
      const scanLimit = clamp(numberFrom(params.get("courtRows")) || 500, 50, 500);
                                                                    ↑ 기본값 500
```

`app.js`는 `courtRows`를 보내지 않는다(확인함). 그래서 기본값 500이 그대로 쓰인다.
실측으로도 확인된다 — 서울 중심 zoom 14에서 `scannedRows`가 1,123이므로 500행씩이면
**3번**이면 끝난다(100행씩이라면 12번이었을 것이다).

**결론: `.env`를 고쳐도 지도 로딩은 빨라지지 않는다. 건드리지 말 것.**

## 그럼 6초는 어디서 오나 — 콜드 스타트다

| | |
|---|---|
| 첫 접속(콜드) | **6.25초** |
| 두 번째(웜) | **0.53초** |

받아오는 양과 무관하다는 증거: 행을 **한 개도 안 받아오는** `/api/viewport-clusters`
(응답 819바이트)도 콜드일 때 8.2초, 웜일 때 0.4초였다. 우리 함수와 크롤러 함수를
깨우는 시간이 대부분이다.

콜드가 다시 오는 때: 한동안 아무도 안 들어왔을 때, 그리고 캐시에 없는 지역으로 옮겼을 때.

### 남은 선택지

- **그대로 둔다.** 느린 건 그 지역 첫 진입 한 번뿐이고 그다음은 0.5초다.
- 짧은 CDN 캐시를 `viewport-properties`에도 건다. 단 아래 "건드리지 말 것"과 충돌하므로
  사용자 판단이 필요하다. (`viewport-clusters`는 이미 s-maxage=300으로 해결했다)

## 원인 2 — 인근 실거래를 동마다 따로 물어봤다 ✅ 해결됨

서울시 실거래가 API는 **구까지만** 서버에서 걸러준다. 동·종별은 받아온 목록에서 고른다.
그래서 동마다 따로 부르면 서버는 같은 구 장부를 반복해서 꺼낼 뿐인데 왕복만 늘어났다.

```
같은 구를 연달아 부를 때
  종로구 창신동 → 1.66초   ← 이때 종로구 전체를 받아옴
  종로구 체부동 → 0.25초   ← 이미 있는 걸 다시 꺼냄
  종로구 무악동 → 0.34초   ← 이미 있는 걸 다시 꺼냄
```

`/api/seoul-deals`에 `picks`를 추가해 한 구 안의 여러 조합을 한 번에 답하도록 했다.
화면은 구 단위로 묶어 부른다.

```
서울 중심 화면(상위 160개 물건)
  예전: 조합마다 1번 → 89번 왕복
  지금: 구마다 1번   →  9번 왕복     (첫 조회 3.2초, 재조회 7ms)
```

같은 조합을 두 방식으로 받아 `scope`·`deals`가 바이트 단위로 일치하는 것을 확인했다.

## 재현 방법

```bash
npm run dev
```

서버를 새로 띄운 직후(= 캐시 빈 상태) 한 번, 그리고 곧바로 한 번 더 잰다.

```bash
curl -s -o /dev/null -w "%{time_total}s\n" \
  "http://127.0.0.1:4173/api/viewport-properties?swLat=37.52&swLng=126.90&neLat=37.61&neLng=127.05&sources=court&exactGeocode=0&zoom=14"
```

첫 번째가 5~6초, 두 번째가 0.5초면 이 문서가 말하는 그 상태다.
`diagnostics.details[0].scannedRows`를 500으로 나누면 실제 왕복 횟수가 나온다.

## 건드리지 말 것

- **`COURT_AUCTION_NUM_OF_ROWS`를 올리지 않는다.** 지도 화면은 이 값을 안 쓴다(위 참고).
  업스트림 상한도 500이라 더 달라고 해도 500만 온다.
- **스냅샷 모드로 되돌리지 않는다.** 빨라 보이지만 법원 물건이 0건이 된다.
  스냅샷 파일은 커밋 `e32fe0b`에서 이미 지워졌고, 되살릴 이유가 없다.
- 캐시 유효시간을 길게 늘려 숫자를 좋게 만드는 것은 답이 아니다. 경매는 최저가와 기일이
  계속 바뀌어서, 오래된 값이 최신인 척 뜨는 것이 느린 것보다 나쁘다.
