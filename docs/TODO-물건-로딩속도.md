# 물건 로딩이 3~5초 느려졌다

**상태:** 원인 확인됨 · 미착수 · 다른 세션에서 처리 예정
**측정:** 2026-09-13 (공매 상세 작업 직후 사용자 피드백에서)
**영향 범위:** `lib/court.mjs`(페이지 크기), `.env`(설정값 한 줄), 그리고 `app.js`의 보조 API 팬아웃

---

## 한 줄로

느려진 게 아니라 **이제야 법원 물건을 실제로 받아오기 시작했다.**
전까지 쓰던 스냅샷 모드는 빨랐던 게 아니라 **0건이라 받을 게 없었다.**

다만 받아오는 방식이 낭비가 커서, 지금 값은 줄일 수 있다.

## 원인 1 — 법원 목록을 100행씩 29번 받는다 (가장 큰 몫)

한 화면에 필요한 행이 2,823개인데 `.env`의 `COURT_AUCTION_NUM_OF_ROWS=100`이라
**약 29번 왕복**한다. `lib/court.mjs`가 8장씩 묶어 병렬로 받지만(동시성 8),
그래도 4파도를 넘어야 끝난다.

업스트림 응답 시간을 직접 재보면 한 번에 더 받는 쪽이 확실히 싸다.

```
limit=100    0.69초   342KB   → 100행
limit=500    1.52초   1.7MB   → 500행
limit=1000   1.12초   1.7MB   → 500행   ← 더 달라고 해도 500이 상한
limit=3000   1.11초   1.7MB   → 500행
```

**상한이 500행이다.** 100 → 500으로 올리면 왕복이 29번에서 6번으로 준다.
첫 장은 직렬이므로 대략 1.5초 + 한 파도 1.5초 ≈ **3초**, 지금의 절반 이하가 된다.

고칠 자리는 `.env`의 `COURT_AUCTION_NUM_OF_ROWS` 한 줄이다. 코드는 이미 그 값을 읽는다
(`lib/court.mjs:67`). **`.env.example`과 배포 환경변수도 같이 올려야** 로컬만 빨라지는 일이 없다.

주의: 한 응답이 342KB에서 1.7MB로 커진다. 서버리스 메모리와 30초 제한 안에 들어오는지
한 번은 실측하고 올릴 것.

## 원인 2 — 인근 실거래를 물건마다 따로 물어본다

`seoul-deals`가 화면 하나에 **32번** 나간다. 자치구·동·종별 조합마다 한 번씩이다.
개별 응답은 빠르지만(최장 1.1초) 합치면 5.4초고, 브라우저 동시 연결을 차지해
정작 급한 `viewport-properties`를 밀어낸다.

같은 자치구·종별 조합이 여러 물건에서 반복되므로 묶어서 한 번에 물어보거나,
상세를 열 때까지 미루는 쪽을 검토할 만하다. **이건 원인 1을 고친 뒤에 다시 재고 판단할 것.**
원인 1만 고쳐도 체감이 달라져서, 여기까지 손댈 값어치가 있는지 다시 봐야 한다.

## 재현 방법

```bash
npm run dev
```

서버를 새로 띄운 직후(= 캐시 빈 상태) 한 번, 그리고 곧바로 한 번 더 잰다.

```bash
curl -s -o /dev/null -w "%{time_total}s\n" \
  "http://127.0.0.1:4173/api/viewport-properties?swLat=37.52&swLng=126.90&neLat=37.61&neLng=127.05&sources=court&exactGeocode=0&zoom=14"
```

첫 번째가 5~6초, 두 번째가 0.01초면 이 문서가 말하는 그 상태다.
`diagnostics.details[0].scannedRows`가 왕복 횟수를 가늠하는 값이다(÷ numOfRows).

## 건드리지 말 것

- **스냅샷 모드로 되돌리지 않는다.** 빨라 보이지만 법원 물건이 0건이 된다.
  스냅샷 파일은 커밋 `e32fe0b`에서 이미 지워졌고, 되살릴 이유가 없다.
  `.claude/launch.json`의 두 설정 모두 API를 쓰도록 맞춰 두었다.
- 캐시 유효시간을 늘려 숫자를 좋게 만드는 것은 답이 아니다. 경매는 최저가와 기일이
  계속 바뀌어서, 오래된 값이 최신인 척 뜨는 것이 느린 것보다 나쁘다.
